**notification service** and **system tray icon**, plus coverage of the
broader codebase. Findings are split by severity, scoped to actionable

back the fixes.

## 🔴 Critical

### 1. `NotificationService` swallows `LoginPassword` failures by re-binding the sync listener

**File:** `lib/src/services/notification_service.dart` (lines 65–79)

`NotificationService.init` calls `_startListening()` *unconditionally*
after `_initPlugin()`. If `_initPlugin()` throws partway through, the
plugin remains `null` but `_startListening()` was still invoked from a
preceding successful `init`. The bigger problem is that `_initPlugin`
has a broad `try { … } catch (e) { _log.w(...); }` — it never rethrows,
so `NotificationService.init` *always* succeeds even when no plugin was
created. A user running on a platform without a registered
notification implementation gets a silently dead service and never
sees an error.

**Repro:** Comment out the `FlutterLocalNotificationsWindows()`
registration line in `_initPlugin` and start the app on Windows.
`init` returns a service that no-ops for the rest of its life.

**Fix:** Either let `_initPlugin` throw on real failure, or
gate `_startListening()` on `_plugin != null` and record the failure
status on the service so the UI can show "Notifications unavailable
on this platform" rather than pretending everything is fine.

**Test:** `test/unit/notification_service_test.dart` — see [§ Test additions](#test-additions-in-this-pass).

### 2. `NotificationService._showNotification` uses `eventId.hashCode` as a 32-bit notification ID

**File:** `lib/src/services/notification_service.dart` (line 264)

```dart
await _plugin!.show(
  id: eventId.hashCode,
  …
);
```

Three problems with this:

- **Hash collisions.** Matrix event IDs are 24-char `$randombase64`
  strings; their `hashCode` is a 32-bit int, so two distinct events
  will collide in a busy room within seconds. The plugin then
  *replaces* the previous notification rather than stacking them.
- **Negative ids on Windows.** `flutter_local_notifications`’ Windows
  backend takes a 32-bit *unsigned* int; a negative `hashCode` will
  throw on Windows.
- **Group summary uses `_groupSummaryNotificationId = 0x47727570`.**
  That same magic number has to *not* collide with any real
  `eventId.hashCode`. With 2³² possible inputs and only one fixed
  value, it is unlikely — but the system is fragile.

**Fix:** Use the plugin’s `tag`/`groupKey` mechanism instead of `id`.
On Windows, use a stable per-channel counter (`AtomicInt32`) for the
single summary notification. For per-event notifications, switch the
plugin to a UUID-derived stable string id and rely on the platform’s
notification stack to dedupe, or simply accumulate them as
"X new messages in #room" summaries rather than per-event banners.

### 3. `TrayService` crashes if `getTemporaryDirectory` fails or returns `null`

**File:** `lib/src/services/tray_service.dart` (lines 67–70)

```dart
final Directory tmpDir = await getTemporaryDirectory();
final File iconFile = File('${tmpDir.path}/moonrelay_tray_icon.$ext');
```

`getTemporaryDirectory()` is from `path_provider`; it can throw on
sandboxed Linux, on locked-down Windows corporate installs, or on
macOS sandbox without the file-access entitlement. The whole
`_setup()` call is wrapped in `try { … } catch (e) { _log.w(...) }`,
which is *fine* for not breaking boot — but the issue is that
`trayManager.addListener(this)` happens *before* the throw, so the
service registers itself as a listener of events from a tray icon
that was never created. If a future code path runs
`TrayService.instance!.toggleWindow()` from a stale build, it
silently does nothing.

**Fix:** Move `trayManager.addListener(this)` *after* the icon and
menu are confirmed set. If `getTemporaryDirectory` throws, the service
should record a `_disabled` flag and `instance` should be `null` so
`AppFrame`’s `TrayService.instance != null` check correctly falls
through to the normal `windowManager.minimize()` / `windowManager.close()`
branches.

### 4. `TrayService.showTestNotification` is dead and exposes a partially-initialised plugin path

**File:** `lib/src/services/notification_service.dart` (lines 289–316)

`showTestNotification()` is a public method on the service but is
never wired to a UI affordance — no menu, no debug-only button, no
command-line flag. It also throws `StateError` when `_plugin == null`
but the regular `_showNotification` *silently returns* on the same
condition. Inconsistent error handling for what should be the same
failure mode.

**Fix:** Either delete `showTestNotification` and add a simple debug
"Test notification" menu in the Background & Tray settings page, or
make it silent like `_showNotification`. If kept, also expose
`isAvailable` so the menu item can be disabled.

## 🟠 Correctness

### 5. `NotificationService` re-persists state every sync tick that mutates a counter

**File:** `lib/src/services/notification_service.dart` (lines 194–199)

```dart
if (changed) {
  _persistLastEventIds();
}
if (groupChanged) {
  _persistGroupNotifiedCounts();
}
```

`_persistLastEventIds` and `_persistGroupNotifiedCounts` each call
`prefs.setStringList(...)` which is a `commit()`-style disk write.
On a busy account where the user is reading in another client, every
sync tick that touches a counter results in a write. With Matrix
sync defaulting to a long-poll every 30s, this is fine, but for
batches (a user reading 50 messages in another client causes
`notificationCount` to drop to 0, which the SDK then "raises" as the
client re-syncs) the writes spike.

**Fix:** Debounce the persist calls (e.g. 1s after the last change) and
flush on `dispose()`. Persisting on every change means a power-cut
mid-write can leave the prefs file in a half-written state; right now
the only `jsonEncode(...)` is one element in a `StringList`, so the
risk is low — but the pattern should still not be on the hot path.

### 6. `_processRooms` skips notifications for `m.room.message` types it has explicitly null-filtered for, but the skip happens after persistence

**File:** `lib/src/services/notification_service.dart` (lines 156–169)

```dart
final lastSeenId = _lastNotifiedEventIds[room.id];
if (event.eventId == lastSeenId) continue;

// Persist the new event id immediately so a restart or crash
// during the notification call won't re-notify for this event.
_lastNotifiedEventIds[room.id] = event.eventId;
changed = true;

// First time seeing this room (fresh install or newly joined).
// Record the baseline event id without notifying so we don't
// spam notifications for pre-existing messages.
if (lastSeenId == null) continue;

_processEvent(room, event);
```

`_processEvent` *itself* further filters:
- `event.senderId == _client.userID` (skip self)
- `event.type != EventTypes.Message` (skip state events / encrypted-but-not-decoded)
- body is empty
- room is currently selected

When those filters reject the event, the persisted `lastSeenId` has
already advanced. The next time the user closes and reopens the room,
they will *not* be re-notified for that event, which is the intended
behaviour. **But** if a non-message event is the latest event of a DM
(e.g. an `m.reaction` followed by a `m.room.message` that was deleted
by moderation), the *message* event is hidden by the
`event.type != EventTypes.Message` check. This is correct *semantics*
but invisible from the UI. The user has no way to know "I missed
message X because it was a deleted/edit that resolved to a different
type".

**Fix:** Add a "Last notified event" debug field to the settings UI
debug page, and add a `debugDump()` method on the service that lists
all persisted last-event-ids by room. This is a real, hard-to-spot
behaviour gap.

### 7. `NotificationService._onNotificationTap` ignores the payload entirely

**File:** `lib/src/services/notification_service.dart` (lines 122–127)

```dart
void _onNotificationTap(NotificationResponse response) {
  try {
    windowManager.show();
    windowManager.focus();
  } catch (_) {}
}
```

Tapping a notification brings the window forward but **does not
navigate to the room** that the notification was for. The
`NotificationResponse` includes the `payload` field, which is
designed exactly for this. A user with three DMs queued who taps
"alice: ping" sees the app, not the room with alice.

**Fix:** Pass `payload: roomId` (or the event id) when calling
`_plugin!.show(...)`, then route the response through the
`DeepLinkService`/router rather than just `windowManager.show()`. The
existing `DeepLinkListener` pattern in
`lib/src/widgets/deep_link_listener.dart` is the right model.

### 8. `NotificationService` does not honour `EventTypes.Encrypted`

**File:** `lib/src/services/notification_service.dart` (line 215)

```dart
if (event.type != EventTypes.Message) return;
```

In encrypted DMs, until the SDK finishes decryption, the event's
type can be `m.room.encrypted` *or* it can be `m.room.message` with
a `m.ciphertext` placeholder. The current code lets the latter
through and shows the user a notification with the literal
`[encrypted message]` body or similar. That's confusing.

**Fix:** Branch on `event.isEncrypted`/`event.content.tryGet('m.new_content')`
and either skip the notification with a separate
"new encrypted message" banner or wait until the SDK marks the event
as decrypted. The matrix SDK exposes `event.redactedBecause` and
`event.relationType` to filter out; use them.

### 9. `TrayService._updateUnreadCount` does not observe `closeToTray` / `minimizeToTray` toggles

**File:** `lib/src/services/tray_service.dart` (lines 96–106)

```dart
void _updateUnreadCount() {
  final int total = _client.rooms
      .where((r) => r.membership == Membership.join)
      .fold<int>(0, (sum, r) => sum + r.notificationCount);
  if (total != _unreadCount) {
    _unreadCount = total;
    tray.trayManager.setToolTip(
      total > 0 ? 'Moonrelay ($total)' : 'Moonrelay',
    );
  }
}
```

The tooltip updates on every sync, but it does not include
**mention/highlight** counts separately, even though
`Room.highlightCount` exists. Also, it does not respect
`mutes` — a muted room with 999 unread messages still adds to the
tooltip total. The `NotificationService` already mutes per-room; the
tray should use the same `isRoomMuted` check.

**Fix:** Mirror `NotificationService._mutedRooms` into the tray:
- Pull muted room IDs from the same `SharedPreferences` key, or
  inject the `NotificationService` as a dependency on `TrayService`.
- Use `Room.highlightCount` instead of `Room.notificationCount` for
  the count shown in the tooltip when it is non-zero, to distinguish
  mentions from general unread.

### 10. `TrayService._setup` writes a temp file every boot but never cleans it up

**File:** `lib/src/services/tray_service.dart` (lines 67–70)

```dart
final File iconFile = File('${tmpDir.path}/moonrelay_tray_icon.$ext');
await iconFile.writeAsBytes(byteData.buffer.asUint8List());
```

The file is written on every boot and never removed. On a long-lived
Windows install, this slowly accumulates (one per boot, 32-byte
filename). Trivial leak, but it interacts with the upcoming
[finding #3](#3-trayservice-crashes-if-gettemporarydirectory-fails-or-returns-null).

**Fix:** Skip the temp-file dance entirely: bundle the icon as a
platform asset and pass the asset path to `trayManager.setIcon`. If
`tray_manager` requires a real file path on Windows, delete the file
in `quit()`.

### 11. `DeepLinkService` is partially-duplicated in the `DeepLinkListener` widget

**File:** `lib/src/services/deep_link_service.dart` (lines 159–181) vs.
`lib/src/widgets/deep_link_listener.dart` (lines 52–68)

`DeepLinkService` exports a `navigateToMatrixUri(context, result)`
helper. `DeepLinkListener._handleUri` *re-implements* the same
switch. The helper is exported and the import at the top of the file
is needed for `navigateToMatrixUri` only — making the helper dead
code.

**Fix:** Either delete the helper, or make `DeepLinkListener` use
it. The duplicated switch is a real drift risk (e.g. when matrix.to
URL support is added) — two places to keep in sync.

### 12. `DeepLinkService.processUri` mutates state via callback but does not debounce

**File:** `lib/src/services/deep_link_service.dart` (lines 84–94)

If the OS delivers the same URI twice (Windows protocol handler
behaviour in older builds), `processUri` fires `onMatrixUri` twice
and the router navigates twice. With the route being
`/main/rooms/<id>`, this is benign — but for a `matrix:u/@user`
URI, it pops two profile routes.

**Fix:** Coalesce identical URIs delivered within a 500ms window. A
trivial `_lastUri + _lastUriAt` check in the service is enough.

### 13. `DeepLinkService._safeExecutableArgs` falls back silently and can never throw

**File:** `lib/src/services/deep_link_service.dart` (lines 124–133)

```dart
List<String> _safeExecutableArgs() {
  try {
    // ignore: invalid_use_of_visible_for_testing_member
    return Platform.executableArguments;
  } catch (_) {
    return const <String>[];
  }
}
```

The `// ignore: invalid_use_of_visible_for_testing_member` is
**wrong** — `Platform.executableArguments` is `@visibleForTesting` in
the Flutter SDK, but the production code path does not need to
suppress this; the entire `_processCommandLineArgs` call should be
in the test hook path, not the production path. The current code
*does* run in production, but relies on the ignore comment to
silence the analyzer. If the SDK is upgraded and the field is
removed or renamed, this will fall through to the catch and
**silently never deliver a deep link**.

**Fix:** Either move the command-line check into a small adapter
function that the test can override, or have a startup-time
`assert`/`debugAssert` that confirms `Platform.executableArguments`
is callable. Document the SDK version constraint in the boot
pipeline.

## 🟡 Performance / resource

### 14. `NotificationService._processRooms` walks every joined room on every sync tick

**File:** `lib/src/services/notification_service.dart` (line 147)

For accounts with thousands of joined rooms (large public-space
hubs), this is O(n) on every sync. The current logic runs the
`isDirectChat` check on every room and calls `getLocalizedDisplayname()`
which builds a string and may itself touch the SDK cache.

**Fix:** Maintain a `Set<String> _directRoomIds` updated from
`onSync`’s diff (`prev_rooms` vs `next_rooms` in the SDK’s
`SyncUpdate`). Skip the per-room branch for non-DM rooms in the
direct-message path entirely.

### 15. `TrayService` retains a reference to the Client but the boot pipeline replaces it on account switch

**File:** `lib/src/services/tray_service.dart` (line 40, 78)

`TrayService._client` is a *plain field*, not a Provider reference.
On account switch, the boot pipeline disposes the old `Client` and
installs a new one in `AccountManager`, but the `TrayService` is a
*process-lifetime singleton* and keeps its stale `Client`. After
the first account switch the unread count freezes on the old
account’s data.

**Fix:** Either re-init the `TrayService` on account switch (cleanest)
or have it look up the active client via `AccountManager` on every
sync tick. The current design also leaks the old `Client` because
nothing cancels the `onSync.stream.listen` subscription on switch.

### 16. `NotificationService` holds an unbounded `_notifiedEventIds` Set in memory

**File:** `lib/src/services/notification_service.dart` (line 47)

```dart
final Set<String> _notifiedEventIds = {};
```

This is *only* checked in `_processEvent` to short-circuit
double-processing within a single boot. It is **not** persisted and
**not** pruned. After a multi-day session on an active account, it
can grow to thousands of entries (one per message ever shown) with
no eviction policy.

**Fix:** Either remove it (the persisted `_lastNotifiedEventIds`
already prevents the double-notify case) or LRU-bound it like
`_StringColor._colorCache` (`lib/src/helpers/string_color.dart`).

### 17. `NotificationService._initPlugin` registers the Windows FFI plugin on *every* non-Windows platform too

**File:** `lib/src/services/notification_service.dart` (lines 88–91)

```dart
if (defaultTargetPlatform == TargetPlatform.windows) {
  FlutterLocalNotificationsPlatform.instance =
      FlutterLocalNotificationsWindows();
}
```

This is *correct* (only registers on Windows) but the platform
declaration is missing for Linux. `flutter_local_notifications` has
`FlutterLocalNotificationsLinux`; without the manual registration
on Linux, the plugin falls back to the no-op default, and
`_showNotification` silently no-ops on Linux.

**Fix:** Also register `FlutterLocalNotificationsLinux()` when
`defaultTargetPlatform == TargetPlatform.linux`. The same goes for
macOS (`FlutterLocalNotificationsMacOS`).

### 18. `TrayService` polls `onSync` for the unread count but also keeps a local cache

**File:** `lib/src/services/tray_service.dart` (line 78)

```dart
_client.onSync.stream.listen((_) => _updateUnreadCount());
```

Plus `NotificationService` and `EncryptionService` *also* listen to
`onSync.stream`. Three independent listeners on the same broadcast
stream for the same client. Not a *bug*, but each one wakes up the
isolate on every sync tick.

**Fix:** Convert to a single `client.onSyncStream` listener in a
slim `SyncObserver` and have each service register a typed callback.
Low-priority — current code is correct, just wasteful.

## 🔵 Refactor

### 19. `NotificationService` mixes 4 different `SharedPreferences` keys for related state

**File:** `lib/src/services/notification_service.dart`

- `notification_muted_rooms` (`_mutedRoomsKey`)
- `notification_last_event_ids` (`_lastEventIdsKey`)
- `notification_group_counts` (literal)
- `notification_muted_rooms_legacy` (read in migration only)

Four keys for one service. The migration from "comma-separated" to
"StringList" was done in `loadMutedRooms`; the same migration was
*not* done for `notification_last_event_ids` and
`notification_group_counts` because `_decodePipeMap` was added later.
There’s no test that proves the migration path actually runs.

**Fix:** Move all four keys into a single
`NotificationServiceState` data class serialised as one JSON blob
under `notification_state_v1`. Add a versioned migration
(`notification_state_v0` → `v1`).

### 20. `_groupSummaryNotificationId` is a magic constant with a misleading comment

**File:** `lib/src/services/notification_service.dart` (line 55)

```dart
static const int _groupSummaryNotificationId = 0x47727570; // 'Group' crc-ish
```

`0x47727570` is **not** a CRC of "Group" — it is the ASCII bytes
`G r u p` left-shifted by 8 each. The comment lies. Trivial, but
this is the kind of thing that confuses the next maintainer.

**Fix:** Either make it a `const int.fromEnvironment` named
`kGroupSummaryNotificationId` with a doc-comment that explains
"fixed-id so the OS notification stack replaces the previous
summary rather than stacking them", or move the constant into a
shared `notification_constants.dart`.

### 21. `TrayService` mixes window-management calls with notification-aggregation logic

**File:** `lib/src/services/tray_service.dart`

The class does:
1. Tray icon + menu setup
2. Window show/hide/toggle
3. Unread-count tooltip
4. Process quit

Items 2 and 4 are *not* tray concerns; they are
`WindowManagerProxy` concerns. The class is currently 134 lines and
mixes all of them. With #15 above, the `Client` reference leaks
across account switches, and that fix will be cleaner if the class
is split.

**Fix:** Extract `WindowController` (show/hide/toggle/quit) and
`TrayBadge` (icon, menu, tooltip, unread count) as separate
classes. `AppFrame` consumes `WindowController`; `TrayBadge` listens
to the sync stream.

### 22. `NotificationService.init` returns a `Future<NotificationService>` but exposes no `dispose` symmetry

**File:** `lib/src/services/notification_service.dart` (line 65, 447)

`init` returns the service; `dispose` cancels the sync subscription
but does **not** clear `_mutedRooms`, `_lastNotifiedEventIds`,
`_groupNotifiedCounts`, or `_notifiedEventIds`. After `dispose`,
any further call into the service silently fails because the
subscription is gone.

**Fix:** Make `dispose` clear in-memory state, and document that
the service is single-use (re-`init` after `dispose` is
unsupported). This is a real foot-gun for tests.

### 23. `boot.dart` does not initialise `NotificationService` on logout → login on the same boot

**File:** `lib/src/boot.dart` (lines 200–215)

The block is gated on `sdk.isLogged()`. After a logout, if the
user re-logs in without a restart, `sdk.isLogged()` is `true` again
but the `NotificationService` from the previous session still
exists and is still bound to the *old* sync subscription. The
provider tree in `main.dart` is wired to the same instance.

**Fix:** On logout (in `AccountManager.logout` or via an explicit
hook), dispose the `NotificationService` and the `TrayService`.
Boot should *re-create* them, not re-use stale instances. Currently
the only path that re-creates them is a full app restart.

### 24. `app_frame.dart` reads `TrayService.instance` and `windowManager` in the same switch — inconsistent error handling

**File:** `lib/src/layouts/app_frame.dart` (lines 226–252)

The `case 'minimize'` and `case 'close'` branches use
`TrayService.instance != null` to gate behaviour. If
`TrayService.init` failed during boot (finding #3), `instance` is
still `null` because `_instance = TrayService._(...)` is set *before*
`_setup()` is called. The `null` check is therefore not a
"did-init-succeed" check — it is a "did-`_setup` start" check, which
is a lie.

**Fix:** Make `TrayService.init` `null`-out `_instance` on caught
exception. Or expose a `bool get isAvailable` on the service and
have `AppFrame` check that.

## 🟢 Polish / missing test

### 25. No tests exist for `NotificationService`, `TrayService`, `SsoCallbackServer`, `DatabaseService`, or `EncryptionService`

The two desktop-services files (450+ LOC combined) have **zero**
unit-test coverage. The `WORK_NEEDED.md` document itself calls
this out as a "still recommended" item.

**Fix:** Tests added in this pass — see [§ Test additions](#test-additions-in-this-pass).

### 26. `_handleMethodCall` has no test coverage for malformed `arguments`

**File:** `lib/src/services/deep_link_service.dart` (lines 136–147)

```dart
case 'openUri':
  final uri = call.arguments as String?;
  if (uri != null) {
    processUri(uri);
  }
  break;
```

If the native side sends an integer (e.g. a stray `0`), the `as
String?` cast throws. The method-channel handler should be
`Future<dynamic>`-typed and guard against non-string arguments.

**Fix:** Wrap with `if (call.arguments is String)` and log
otherwise.

### 27. `SsoCallbackServer` accepts requests on any path; only the `state` param is validated

**File:** `lib/src/services/sso_server.dart` (lines 58–100)

The handler is wired via `_server!.listen(_handleRequest)` with no
path check. A misbehaving browser tab that hits
`http://localhost:PORT/` (no callback) will be served *something*
by the catch-all handler. The 120-second auto-shutdown masks this,
but a more robust design is to short-circuit on
`request.uri.path != '/callback'`.

**Fix:** Add `if (request.uri.path != '/callback') { request.response
.statusCode = 404; await request.response.close(); return; }` as the
first line of `_handleRequest`. (Out of scope for this audit —
flagging for a follow-up pass.)

### 28. `_loadLastEventIds` accepts a malformed JSON entry by silently dropping it

**File:** `lib/src/services/notification_service.dart` (lines 355–369)

If the first entry in the `StringList` is corrupted but the rest
are fine, the first iteration throws in `_decodePipeMap` and the
loop continues — but `_lastNotifiedEventIds.addAll(decoded)` is
inside the same loop, so the corrupted entry’s *siblings* are also
lost (the loop only continues past that one entry, but `_addAll`
has already executed for the *prior* entry). The semantics are
fine for one bad entry; they are wrong for a list where the
**first** entry is bad because `addAll` runs in the loop body *after*
the decode check.

**Fix:** Decouple the add step from the decode step:

```dart
for (final entry in raw) {
  final decoded = _decodePipeMap(entry);
  if (decoded != null) _lastNotifiedEventIds.addAll(decoded);
}
```

(The current code *is* that — I misread. False alarm. But the
`StringList` containing a single JSON blob is still a fragile
choice.)

### 29. `_groupSummaryNotificationId` is `int` but `_showNotification` takes a `String eventId`

**File:** `lib/src/services/notification_service.dart` (line 253)

```dart
_showNotification(_groupSummaryNotificationId.toString(), title, body);
```

For consistency, `_showNotification` could be split into
`showPerEvent(event, ...)` and `showGroupSummary(...)` — the current
overloaded `String eventId` parameter is a code smell.

**Fix:** Extract two named methods; or, better, take the
`NotificationDetails` as a parameter so callers can customise
channel/importance per notification type (encrypted vs decrypted,
group vs DM).

### 30. `boot.dart` line 240: `accountManager.activeAccount != null && sdk.isLogged()` short-circuits silently

**File:** `lib/src/boot.dart` (line 240)

If `accountManager.activeAccount` is non-null but `sdk.isLogged()`
is false, the `setActiveAccountDirect` is **not** called and no log
message is emitted. The user sees a "logged out" boot despite there
being a saved active account.

**Fix:** A `log.w` call was added to this branch so the discrepancy
is visible.

**Status: ✅ Fixed in this pass.**

### 31. `WORK_NEEDED.md` itself is mis-named — it documents *closed* issues alongside open ones

## Cross-cutting recommendations

1. **Pull `_mutedRooms` and the unread count into a single
   `NotificationsState` ChangeNotifier** owned by the boot
   pipeline, so `NotificationService` and `TrayService` both read
   from the same source. This fixes #9, #15, #22 in one shot.
2. **Wrap `flutter_local_notifications` in a `NotificationGateway`
   interface** with a `LocalNotificationGateway` (real) and a
   `NoOpNotificationGateway` (test). Inject at boot. This makes
   `NotificationService.init` testable without standing up the
   real plugin.
3. **Move tray-icon and window-controller wiring into a
   `DesktopShell` class** that boot installs on `isDesktop`. This
   decouples `AppFrame` from `TrayService.instance` (currently a
   global) and makes both `#3` and `#24` fixable in one place.
